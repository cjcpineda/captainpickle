# League Captain

AI lineup strategist for **Cross Club Pickleball** captains. Captains sign in, see their team's schedule and results, and chat with an AI strategist that can read the league database.

**What's here:**
- **Schedule:** the next match (home/away, division, time, location) with its lineup deadline, upcoming matches, and past results with game-by-game lineups.
- **Scouting report:** for the next opponent, their roster with records, the pairs they use most, their strongest players, and a button that asks the AI for counter-pairings.
- **Practice:** upload practice games (any file; see below), check how they were read, then save. Lists every pair's record across league and practice, A–Z.
- **AI Strategist:** a chat that reads all of the above from the database.

CPL lineup deadlines: away teams submit two nights before the match, home teams the night before, always at 7:30 PM Eastern (`lib/deadline.ts`).

## Quick start

Requires Node 22.13+ and a Cloudflare account. The AI runs on [Workers AI](https://developers.cloudflare.com/workers-ai/), so there's no API key; run `npx wrangler login` once so `npm run dev` can reach it.

```bash
git clone https://github.com/cjcpineda/captainpickle.git
cd captainpickle
npm install
npx wrangler login                # Workers AI runs on Cloudflare, even in local dev
npm run db:migrate                # creates the local D1 database
npm run captain -- you@example.com "Your Name" "Your Team Name" <password> --division "NJ / PA 4.0"
npm run sync                      # pulls your schedule and results from CPL
npm run dev                       # http://localhost:3000
```

| Command | What it does |
| --- | --- |
| `npm run dev` | Day-to-day local development (uses `.env`) |
| `npm run preview` | Run locally inside the real Cloudflare Workers runtime (copy `.dev.vars.example` to `.dev.vars` first) |
| `npm run sync` | Pull the latest CPL data into the local database |
| `npm test` | Run the tests |

Your computer and Cloudflare have **separate databases**. `npm run dev` and `npm run sync` use the local one; the live site uses D1 on Cloudflare. To fill either one with CPL data, sign in and press **Sync now** on the Schedule page: it syncs the database of the site you're on. On Cloudflare the sync also runs by itself every six hours (cron in `wrangler.jsonc`).

## Deploy to Cloudflare

```bash
npx wrangler login
npm run db:migrate:remote
npm run deploy
npm run captain -- you@example.com "Your Name" "Your Team Name" <password> --division "NJ / PA 4.0" --remote
```

First deploy on a new account: run `npx wrangler d1 create captainpickle` and paste the printed `database_id` into `wrangler.jsonc`. After changing bindings, run `npm run cf-typegen`.

### Deploying from GitHub (Workers Builds)

In the Cloudflare dashboard, under your Worker's **Settings → Build**:

| Setting | Value |
| --- | --- |
| Build command | `npx opennextjs-cloudflare build` |
| Deploy command | `npx wrangler deploy` |
| Worker name | `captainpickle`, the `name` in `wrangler.jsonc` (they must match) |

No secrets are needed: the AI uses the Worker's `AI` binding (in `wrangler.jsonc`). To try another model, add `AI_MODEL` under **Settings → Variables and Secrets**.

Keep each D1 binding in `wrangler.jsonc` local (no `"remote": true`). The AI binding is always remote, so `next.config.ts` loads bindings only for `next dev`; during a build, a remote binding would make the build server try to log in to Cloudflare and fail.

`cloudflare-env.d.ts` is generated by `npm run cf-typegen`; don't edit it by hand. Secrets and optional settings are declared in `env.d.ts`.

## How it fits together

| Piece | Where |
| --- | --- |
| Schedule page (next match, deadline, upcoming, results) | `app/(app)/page.tsx` |
| Scouting report page | `app/(app)/scouting/page.tsx`, `lib/scouting.ts` |
| Practice uploads and pair records | `app/(app)/practice/`, `components/PracticeUpload.tsx`, `lib/practice.ts` |
| AI Strategist chat UI | `components/Chat.tsx`, `components/Strategist.tsx` |
| Streaming chat endpoint (NDJSON) | `app/api/chat/route.ts` |
| Agent loop: Workers AI plus tools, chats saved per captain | `lib/strategist/agent.ts` |
| Tools the AI can call (schedule, rosters, match sheets, scouting, player history) | `lib/strategist/tools.ts` |
| CPL sync (schedule, match sheets, players) | `lib/cpl.ts`, `lib/cpl-schedule.ts`, `custom-worker.ts` (cron) |
| D1 schema and queries | `migrations/`, `lib/db.ts`, `lib/repo.ts` |
| Captain auth (scrypt passwords, session cookie) | `lib/auth.ts`, `lib/password.ts` |

The strategist runs on Cloudflare Workers AI (`lib/ai.ts`), through the Worker's `AI` binding: no API key, and usage counts against the account's free daily allowance (10,000 neurons) before Workers Paid billing. The default model is `@cf/zai-org/glm-4.7-flash`; set `AI_MODEL` to any Workers AI model with function calling to change it (`@cf/moonshotai/kimi-k2.6` is stronger but uses the allowance faster). Photos of scoresheets go to `@cf/meta/llama-4-scout-17b-16e-instruct` (`AI_VISION_MODEL`). The strategist answers only from what its tools return, so every score, pairing and date it quotes comes from the database.

## Data from CPL

crossclubpickleball.com is a single-page app backed by a public, read-only JSON API. The sync (`lib/cpl.ts`) reads the same data the Lineups page shows:

- **Schedule:** every upcoming match for each captain's team, with date, time, home/away and address.
- **Match sheets:** every completed match involving your team or one of your upcoming opponents, game by game, with each player's gender.

A match is downloaded once and never re-fetched, so routine syncs make only a couple of requests. Forfeited games (no players listed) are skipped.

### Divisions

Every team belongs to one CPL division, and each captain sees only their own division: their schedule, results, roster, player records, scouting reports and the AI Strategist's lookups all come from it. Clubs often field a team with the same name in several divisions (Pickleball Kingdom Tinton Falls plays in 3.0, 3.5 and 4.0), so a team is a name *within* a division, and those are separate teams in the database.

Pick the division when you add the captain, using the name the league site shows:

```bash
npm run captain -- mike@example.com "Mike Alfaro" "Pickleball Kingdom Tinton Falls" <password> --division "NJ / PA 3.0"
```

Leave out `--division` and the script looks the team up on CPL; if the name plays in more than one division, it lists them for you to choose. Running the command again for an existing email moves that captain to the new team and division. Then press **Sync now** (or `npm run sync`) to pull that division's data.

## Practice data

Captains upload practice games from the Practice page. Nothing is saved until they've checked the preview.

- **CSV template** (`public/practice-template.csv`): one row per game with `date, player_a1, player_a2, player_b1, player_b2, score_a, score_b`. Read directly, no AI. `date` may be blank; the captain picks one on upload.
- **Anything else:** another CSV layout, a text file, a PDF, or a photo of a scoresheet. Workers AI reads the games out of it (PDFs are converted to text first). For Excel, save as CSV first.

Typed names are matched to the roster: exact name, then a unique first name, last name or prefix ("Chelsea" → Chelsea Convissar). Names that match no one are flagged in the preview and added as new players. Practice games never count toward league results. The AI Strategist sees them, separately from league games.
